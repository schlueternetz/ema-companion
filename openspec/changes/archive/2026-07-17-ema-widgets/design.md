## Context

EMA Companion already fetches and caches hourly and daily production data through `HourlyEnergyRepository` and `DailyEnergyRepository` (see `feature/home/HomeFragment.kt`), each with its own throttle, persisted cache, and `ThrottleResettable`/factory-reset integration (ADR-007). This design adds three home-screen widgets (a today's-hourly-production line chart, a today/month/last-30-days number summary, and a daily-history bar chart) built directly on those existing repositories instead of any new storage or networking, and picks **Jetpack Glance** (user-confirmed) as the widget UI framework — the first Compose usage in a project that is otherwise 100% View/XML (per AGENTS.md Stack).

Companion's EMA API usage is governed by a shared monthly budget (ADR-009, 1,000 calls/month, currently ~360 allocated, ~640 headroom). Any new trigger that calls `refresh()` on an existing repository must be justified against this budget, per AGENTS.md's "EMA API call budget" rule.

## Goals / Non-Goals

**Goals:**
- Ship three Glance widgets showing today's hourly production, a today/month/last-30-days summary, and daily production history.
- Reuse `HourlyEnergyRepository`/`DailyEnergyRepository` as the sole data source — zero new network client, zero new local database.
- Keep widgets usable without opening the app (background refresh), while staying inside the existing shared EMA API budget.
- Keep widgets accurate immediately after a settings change (credential edit, import, factory reset), not just on the next scheduled trigger — a widget has no "revisit" moment to naturally pick up new settings the way `HomeFragment` does.
- Follow existing conventions: feature-first package (`feature/widgets/`), ADR-006 error/placeholder behavior, ADR-007-style throttle/reset integration.

**Non-Goals:**
- Per-widget configuration screens — Companion has one system/credential set, configured once in Settings.
- A separate local database, chart renderer, or activity log for widgets — Companion's equivalents already exist and are reused.
- Real-time (sub-hour) widget freshness — these are glanceable summaries, not a live dashboard.
- Any change to `HourlyEnergyRepository`/`DailyEnergyRepository`'s public contract — widgets are a read-only third caller alongside `HomeFragment` and (for Hourly) the new refresh worker.
- A night-time (or sunrise/sunset-based) gate on the background worker — a legitimate future optimization (see Decision 5, Open Questions), deliberately left to a separate, later OpenSpec change so this one stays focused on the widgets themselves.

## Decisions

### 1. Jetpack Glance for widget UI (user-confirmed)
`androidx.glance:glance-appwidget` added as a new dependency, scoped to `feature/widgets/`. This is the first Compose code in the project. **Risk**: the project currently has no Kotlin Gradle plugin at all — Kotlin compilation comes from AGP 9.2.1's built-in Kotlin support (`settings.gradle.kts`/`app/build.gradle.kts` apply only `com.android.application`, no `org.jetbrains.kotlin.android`). Enabling Compose normally requires the separate Compose Compiler Gradle plugin (`org.jetbrains.kotlin.plugin.compose`), and its compatibility with AGP's built-in-Kotlin mode (rather than the traditional standalone Kotlin plugin) is unverified. **Mitigation**: the first implementation task is a build spike — add the Glance dependency and Compose compiler plugin, compile one trivial widget, and confirm the build succeeds before any functional work starts. If incompatible, fall back to classic RemoteViews (already scoped as the rejected alternative below) and update this design.

### 2. Charts rendered as an off-screen bitmap using the existing MPAndroidChart library
Glance (like RemoteViews) cannot host a live custom `View` — chart content must be a `Bitmap` displayed via Glance's `Image` composable. This design reuses **MPAndroidChart** (already a Companion dependency, already styled to match `HomeFragment`'s hourly line chart and history bar chart) by instantiating a detached `LineChart`/`BarChart`, measuring/laying it out off-screen at the widget's target pixel size (from `SizeMode.Responsive`/`LocalSize.current` in Glance), binding the same data + styling as `HomeFragment`, and calling `chart.draw(canvas)` into a `Bitmap`.
- **Alternative considered**: hand-rolled raw `Canvas` drawing. Rejected — duplicates axis scaling, month-color palette, and dashed-current-hour logic that already exists and is tested for `HomeFragment`'s charts; two independent chart implementations would drift.
- **Alternative considered**: Glance's own `Canvas`-less declarative shapes (bars as stacked `Box`es). Rejected — cannot reproduce a continuous line chart with a projected dashed segment, and would still need a second implementation of the bar/line rendering logic.

### 3. Widget package structure
New `feature/widgets/` package (ADR-004): `GlanceAppWidget`/`GlanceAppWidgetReceiver` pairs for the three widgets, the bitmap chart renderer, and `WidgetRefreshWorker`. The renderer stays in `feature/widgets/` rather than `core/` — only widgets consume it (`HomeFragment` uses live MPAndroidChart views, not bitmaps); per ADR-007's precedent, extract to `core/` only if a third consumer appears.

### 4. Widgets read `currentState()` only — never trigger a fetch on their own render pass
Chart scaling reuses the **same** `SettingsRepository` values `HomeFragment` already reads — `getSystemCapacity()` for both charts' Y-axis maximum, and `getHistoricDataDays()` for the History widget's window/title — read fresh on each `provideGlance` composition. There is no widget-local copy of these settings and no new preference; changing System Capacity or Historic Data Days in Settings is reflected the next time a widget recomposes (its own periodic update, or the next foreground/background refresh trigger), exactly as it already affects the Home screen's charts.

Matches the tile-repository pattern (ADR-007): `GlanceAppWidget.provideGlance` calls `HourlyEnergyRepository.create(context).currentState()` / `DailyEnergyRepository.create(context).currentState()` synchronously (SharedPreferences read, no network), exactly like `HomeFragment.onViewCreated`'s initial render. Widgets never call `refresh()` directly — all fetching is centralized in two triggers described below, so there is exactly one place that decides when a network call happens per repository (unchanged from today, `HomeFragment` + the new worker).

### 5. Three refresh triggers, chosen to keep Hourly/Daily cadence bounded and predictable
- **Foreground**: `HomeFragment` already calls `hourlySource.refresh()`/`dailySource.refresh()` on `onResume`/pull-to-refresh. After each completes, it now also calls `WidgetUpdater.updateAll(context)` (Glance's `GlanceAppWidgetManager` + `update()`), so opening the app refreshes widget content immediately.
- **Background**: a new `WidgetRefreshWorker` (`CoroutineWorker`, modeled directly on the existing `ModuleHealthWorker`):
  - Hourly: periodic every 2 hours, all day, calling `HourlyEnergyRepository.refresh(force = false)` — the existing 1-hour throttle still governs whether a network call actually happens. **Out of scope for this change**: a night-time (or sunrise/sunset-based) gate that skips triggers when there's no solar production to fetch — a legitimate future optimization, but kept as a separate, later OpenSpec change so this one stays focused on shipping the widgets themselves. Current cadence is still comfortably within the ADR-009 budget (see Decision 6).
  - Daily: once per day at a fixed time (21:00, same alignment approach as `ModuleHealthWorker`'s 8pm check), calling `DailyEnergyRepository.refresh(force = false)` — History/Summary month and last-30-days totals don't need intraday freshness.
  - After each successful refresh, calls `WidgetUpdater.updateAll(context)` so on-screen widgets reflect the new cache without waiting for Glance's own periodic update cycle.
- **Settings change**: `SettingsFragment.invalidateApiThrottle()` is already the single choke point called after every per-field credential/base-URL edit (4 call sites) and from `refreshAllDisplayedValues()` (import + factory reset) — it already resets throttle on `hourlyEnergyRepository`/`dailyEnergyRepository` alongside the other tile repos (both are already in `tileRepositories`, confirmed in the current code). It now *also* launches a `lifecycleScope` coroutine that calls `hourlyEnergyRepository.refresh(force = true)` and `dailyEnergyRepository.refresh(force = true)`, then calls `WidgetUpdater.updateAll(context)` regardless of outcome. This closes a gap specific to widgets: `HomeFragment` naturally gets a fresh, throttle-reset fetch the next time the user visits Home after a settings change, but a widget sitting unattended on the home screen has no equivalent "revisit" moment — without this, it could keep showing a *different* (or no-longer-valid) system's stale numbers for as long as the next background-worker trigger (up to several hours away). Factory reset also clears credentials (`repository.clearAll()`), so the forced refresh there resolves to `ConfigurationError` (no network call, free — does not touch the ADR-009 budget) and the widgets correctly fall back to the "not configured" placeholder via the same `updateAll()` call; no special-casing is needed for that path.
- **Today's total is derived from the Hourly snapshot** (`snapshot.hours.values.sum()`, same computation `HomeFragment` already does), not from `DailyEnergyRepository` — so the Production Summary widget's "Today" figure only depends on the frequently-refreshed Hourly cache, and the Daily repository genuinely only needs its once-daily trigger for month/last-30-days totals and the history bar chart.
- **Background refresh benefits `HomeFragment` too, for free**: `WidgetRefreshWorker` calls the exact same `HourlyEnergyRepository`/`DailyEnergyRepository` instances (same `SharedPreferences`-backed cache) that `HomeFragment` reads via `currentState()` and writes via its own `refresh()`. There is one persisted cache per repository, not one per caller. So when the user reopens the app after the background worker has run, `HomeFragment.onViewCreated`'s synchronous `currentState()` render already reflects the background-fetched data, and its own `onResume` `refresh()` call is throttled into a no-op (same 1-hour/throttle window) rather than issuing a redundant fetch. No new plumbing is needed for this — it falls out of both callers sharing one repository instance per app process.

### 6. ADR-009 budget impact
The Hourly repository now has a dominant, worker-driven trigger cadence instead of an app-open-driven one. Revised allocation (2-hour interval, no time-of-day gating ⇒ 12 triggers/day, each satisfying the existing 1-hour throttle):

| Feature | Endpoint | Throttle | Calls/trigger | Triggers/day | Calls/month |
|---|---|---|---|---|---|
| Today hourly chart + widgets (revised) | `getHourlyEnergy` | 1 hr | 1 | ~12 (widget worker, every 2h, no gating; app opens absorbed by same throttle) | ~360 |
| History daily chart + widgets (unchanged, worker replaces app-open trigger 1:1) | `getDailyEnergy` | 1 hr | 1 (steady state) | 1 | ~30 |

Net change: **+210/month** (Hourly line moves from ~150 to ~360; Daily line unchanged). New running total ≈ 570/month, headroom ≈ 430/month. This row must be applied to ADR-009 as an implementation task before/alongside shipping. A future night-time-gate change (see Decision 5) would bring this back down closer to the daylight-only estimate (~240/month) by skipping triggers with no chance of new production data — deliberately deferred rather than bundled into this change.

### 7. Unconfigured state matches ADR-006's silent `ConfigurationError`; fetch errors replace content instead of a co-existing inline line
If `SettingsRepository.isConfigured()` is false, all three widgets show a neutral "Not configured — open EMA Companion" placeholder (no chart, no numbers) instead of attempting to read a cache that was never populated — consistent with `ConfigurationError` being silent elsewhere in the app.

If EMA is configured but the latest fetch failed (whether the triggering call was the foreground refresh or the background worker), the widget **replaces its entire content area — chart or figures — with an error message** (distinguishing network / authentication / other, reusing the same `FetchError` categories and copy already used by the Home screen tiles) instead of showing the last cached value. This is a deliberate departure from ADR-006's Home-tile pattern (last value + a small inline error line): ADR-006 is scoped to in-app tiles, which have room for both a value and a status line; a home-screen widget does not, and showing a chart that might be hours or days stale with no visible indication is worse than a clear "Couldn't update — check connection" message. The error message clears and the widget reverts to normal content as soon as a subsequent refresh succeeds.
- **Alternative considered**: keep ADR-006's pattern verbatim (last value + inline error line) at a smaller type size. Rejected — at typical widget sizes (the smallest is 40dp tall) there is no legible room for a second line alongside a chart or three numbers; this was the design's original assumption but is overridden by this decision.

### 8. Widgets follow the app's Display Mode preference, not just the system theme
Widgets read `SettingsRepository.getDisplayMode()` (`"system"|"light"|"dark"`, the same persisted value the `dark-mode` capability already applies via `AppCompatDelegate.setDefaultNightMode`) directly in `provideGlance`, rather than relying on the widget-hosting process's ambient theme. This matters because Glance widget composition runs in the app's own process but is *not* an Activity — it does not automatically inherit `AppCompatDelegate`'s applied night mode, which is Activity/resource-configuration-oriented. Concretely:
- `"system"` → use Glance's day/night-aware default (`GlanceTheme.colors`, which follows the device's `Configuration.uiMode` like any other day/night-aware Android surface).
- `"light"` / `"dark"` → explicitly supply a fixed light or dark `ColorProviders` scheme to the widget's root composable, regardless of the device's current system theme, matching what the user already forced inside the app.
- Widget appearance updates the next time the widget recomposes (its own periodic update, or the next foreground/background refresh trigger) after the user changes the setting — not necessarily instantly, unlike the in-app instant switch (ADR/`dark-mode` spec requirement is Activity-scoped).
- **Risk**: the exact mechanism by which Glance determines "system" day/night in a widget (vs. an Activity) is unverified pre-implementation — flagged as an Open Question, resolved during the same build spike as Decision 1.

### 9. Tap target: Home normally, Settings when unconfigured or showing an error
Each widget's `PendingIntent` opens `MainActivity`, but the destination depends on that specific widget's own state at the moment the `PendingIntent` is built (during `provideGlance`):
- **Not configured, or the widget's latest fetch resulted in an error** → target Settings, where credentials are edited and the API call log (`api-call-log` capability) lives, so the user can act on or diagnose the problem directly.
- **Otherwise** (normal data on display) → target Home, same as before.

**Mechanism**: the widget's `Intent` carries a plain extra (`EXTRA_WIDGET_TARGET = "settings" | "home"`). After `MainActivity.onCreate`'s existing `configured`-driven graph/bottom-nav setup completes, it reads this extra if present and selects the corresponding bottom-nav item (`bottomNav.selectedItemId = R.id.settingsFragment` or `R.id.homeFragment`), then clears the extra from the intent so a later recreation (e.g. rotation) doesn't re-trigger the navigation.
- `MainActivity` already forces Settings as the start destination whenever `!repository.isConfigured()`, independent of any intent extra — so the "not configured" half of this behavior is already correct even without the extra. The widget still explicitly requests Settings in that case too: partly for clarity (the intent matches the actual outcome), and because the "error while configured" half has no such automatic fallback and genuinely needs the extra to work at all.
- **Alternative considered**: `androidx.navigation.NavDeepLinkBuilder` to construct a PendingIntent that targets `R.id.settingsFragment`/`R.id.homeFragment` directly. Rejected — its automatic deep-link consumption would race against `MainActivity.onCreate`'s own custom graph-swap-when-unconfigured logic, and the ordering between `NavHostFragment`'s deep-link handling and the manual `navController.graph = graph` reassignment is not obviously well-defined here. The plain-extra + `bottomNav.selectedItemId` approach instead reuses an already-exercised navigation path (bottom-nav selection via `NavigationUI`) with one clear, explicit ordering.

## Testing Strategy

Widgets themselves cannot be driven by Maestro (or Espresso) — a home-screen widget is hosted by the launcher in a separate window, so no E2E tool that drives the app's own Activity window can inspect or tap one. Verification is therefore layered as:

- **Unit (plain JUnit)**: pure-logic pieces with no Android dependency — the `FetchError`→message mapper, the widget's tap-target decision (state → `"home"`/`"settings"`).
- **Robolectric (the primary layer for anything widget-shaped)**:
  - Widget content composition: invoke each `GlanceAppWidget`'s composable/`provideGlance` directly against a seeded `SharedPreferences` state and assert on the resulting content (chart present vs. error message vs. placeholder), exactly as already planned in tasks 4–6.
  - `WidgetRefreshWorker`: `TestListenableWorkerBuilder`, same pattern as the existing `ModuleHealthWorkerTest`.
  - `SettingsFragment` → widget reaction: a test seam (companion override, matching `ModuleHealthRepository.repoOverride`/`GmailSmtpEmailSender` overrides elsewhere) lets a test substitute a fake `WidgetUpdater` and assert `updateAll()` is invoked after a credential edit, an import, and a factory reset — including the factory-reset case resolving to the "not configured" placeholder path.
  - `MainActivity` tap-target routing: build the Activity via Robolectric with the `EXTRA_WIDGET_TARGET` intent extra set, and assert the resulting `NavController.currentDestination` — mirroring the project's existing lesson that bottom-nav navigation must be tested through the real selection path, not a bare `navController.navigate(id)` call.
  - The settings-change → forced-refresh → widget-update path end-to-end: reuse the `MockWebServer` pattern already used for `HourlyEnergyRepositoryTest`/`DailyEnergyRepositoryTest` so the `force = true` refresh exercises a real HTTP round trip against a fake server, then assert `WidgetUpdater.updateAll()` fires afterward.
- **Maestro**: none added for widgets specifically (not reachable from the app's window). Existing Settings and Home Maestro flows must continue to pass unaffected by the new code running in the settings-save path (`/qa`); any visual confirmation of tap-target routing (does tapping actually land on Settings vs. Home on a real device) is a one-time manual/emulator check (task 10.2), not an automated flow.

## Risks / Trade-offs

- **[Risk] Glance/Compose may not build cleanly under AGP 9.2.1's built-in-Kotlin mode (no standalone Kotlin plugin currently applied)** → Mitigation: first task is a build spike proving this before functional work begins; RemoteViews is the documented fallback.
- **[Risk] Off-screen MPAndroidChart rendering (measure/layout a detached view, then `draw()` to a `Bitmap`) is a less common usage pattern than an attached, on-screen chart** → Mitigation: unit-test the renderer's output at a small set of fixed widget pixel sizes; visually confirm on-emulator once per widget (per AGENTS.md debugging discipline — emulator reserved for final visual confirmation, not exploration).
- **[Trade-off] The background worker fires every 2 hours around the clock, including hours with no solar production, spending part of the ADR-009 budget for no benefit** → Accepted for this change to keep scope focused on the widgets themselves; still well within budget (~430/month headroom remaining). A night-time (or sunrise/sunset-based) gate is a natural, separately-scoped follow-up change (see Decision 5).
- **[Trade-off] Replacing the chart/figures with an error message means the last-known-good value is momentarily not visible while an error is showing** (unlike Home tiles, which keep the value alongside the status line) → Accepted per Decision 7: at widget sizes there isn't room for both, and the value reappears automatically on the next successful refresh; the app's Home screen remains the place to see the last good value plus error detail together.
- **[Risk] Glance's day/night resolution inside a non-Activity, app-process widget composition is unverified** → Mitigation: confirm during the build spike (task 1) whether `"system"` mode needs an explicit `Configuration.uiMode` check instead of relying on Glance's default day/night `ColorProviders`.
- **[Trade-off] Maestro cannot drive home-screen widgets (outside the app's window)** → widget content-composition functions and `WidgetRefreshWorker` are covered by unit/Robolectric tests; no E2E flow is added for widgets, consistent with "Maestro for a small set of critical UI flows only" (ADR-002).
- **[Risk] The `EXTRA_WIDGET_TARGET` intent extra must be consumed exactly once** (cleared immediately after `MainActivity` acts on it) to avoid re-navigating to Settings/Home on an unrelated Activity recreation (rotation, process death + restore) → Mitigation: clear the extra right after reading it; cover with a Robolectric test that recreates the Activity and confirms no second navigation occurs.

## Migration Plan

Purely additive — no existing data, screens, or specs change. Widgets can be added to a home screen only after this ships; no migration of existing users' state is needed. Rollback is a plain revert (remove the new package, dependency, manifest receivers, and worker registration).

## Open Questions

- Exact Compose/Compose-Compiler and Glance version pins compatible with AGP 9.2.1 + Gradle 9.5.1 — resolved during the build spike (task 1), not blocking design approval.
- Whether/when to add a night-time (or sunrise/sunset-based) gate to `WidgetRefreshWorker`'s hourly trigger, and whether its bounds should be a fixed constant or a user-configurable preference (like `historyDays`) — intentionally deferred to a separate, later OpenSpec change so this one stays focused on the widgets themselves. Note: the *tiles themselves* (`HomeFragment`) have no clock-hour gate at all — they fetch whenever the user visits Home, any time of day, subject only to the existing throttle; any future gate would be new, background-worker-specific behavior, not a change to tile behavior.
- Exact API for forcing Glance's day/night resolution to match an explicit Light/Dark override (vs. its system-default behavior) — resolved during the build spike (task 1).
