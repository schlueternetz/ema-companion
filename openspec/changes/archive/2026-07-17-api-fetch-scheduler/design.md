## Context

Three independent places currently decide when to fetch hourly/daily/module-health data, each unaware of the others:

1. **`HomeFragment`** — `onViewCreated()` seeds from `currentState()` (no network); `onResume()` launches three parallel `viewLifecycleOwner.lifecycleScope.launch { repo.refresh(force=false) }` coroutines (module health, hourly, daily), gated by `isXDataNeeded()`; `onPullToRefresh()` does the same with `force=true`.
2. **`SettingsFragment.invalidateApiThrottle()`** — called from 7 separate call sites (one per credential-affecting field's `onSave`, the Base URL reset button, and the "Use local stub" button), each independently doing `tileRepositories.forEach { it.resetThrottle() }` then launching its own coroutine that force-refreshes hourly+daily and calls `widgetUpdateAction()`.
3. **`WidgetRefreshWorker`** (periodic, every 2h) and **`ModuleHealthWorker`** (periodic, daily at 8pm array-local) — each does its own `isXDataNeeded()` gating and calls `refresh(force=false)` independently of the other two.

This scattering caused a confirmed bug (see proposal): editing two-plus connection-setting fields in a row fires multiple redundant hourly/daily fetches for the same data, and whichever one *finishes last* wins — if that one fails, it overwrites a moments-earlier success with an error, discovered when it collided with the local `ema-api-stub`'s single-use canonical interaction (CI Maestro `a-home-screen.yaml` failure) but equally reproducible against the real EMA API on a bad network moment. `viewLifecycleOwner.lifecycleScope`-bound fetches also die if the user navigates away from Home mid-fetch, silently dropping a legitimately-due, throttle-respecting request.

## Goals / Non-Goals

**Goals:**
- One component (`ApiSyncScheduler`) is the only thing frontends call to request a refresh; no Fragment or Worker calls `repository.refresh()` directly.
- A burst of requests for the same data (e.g. several Settings field saves in a row) collapses into exactly one resulting fetch per data source, regardless of how fast or slow the burst is.
- A requested fetch is not cancelled by unrelated UI lifecycle events (Fragment view destroyed, user navigates away) — it runs to completion in the background once accepted.
- Existing `isHourlyDataNeeded()`/`isDailyDataNeeded()` gating (from `configurable-tiles-widgets`, "does any enabled tile/widget *consume* this?") is preserved, but the background periodic poll additionally gates on whether a consuming widget is **actually placed** on a home screen (`GlanceAppWidgetManager.getGlanceIds()`), not just enabled in Settings — a type being enabled but never dragged onto a home screen shouldn't keep a background job alive.
- **Module Health is the one data source that is never gated by app-open state, widget placement, or even its own tile's enabled checkbox** — alerting (email/push) is a distinct feature from the Home tile's visibility, and must keep running in the background unconditionally. This matches `ModuleHealthWorker`'s existing behavior (it was never touched by the `configurable-tiles-widgets` gating) — this design makes that invariant explicit and tested rather than an accident of scope.
- Optimize the background hourly/daily poll cadence for freshness within budget: poll only during the array's daylight production window (06:00–22:00 array-local) rather than uniformly 24/7 — overnight polling burns budget for data that cannot have changed. See the proposed schedule below.
- Home's own on-demand (`onResume`/pull-to-refresh) triggers are **not** time-of-day-gated — an explicit user action always gets a real attempt, subject only to the repository's own throttle; the daylight window applies solely to the *unattended background* poll.

**Non-Goals:**
- Changing `ModuleHealthRepository`'s own throttle/caching internals, or the SharedPreferences schema/per-day cache keys of `HourlyEnergyRepository`/`DailyEnergyRepository` (ADR-007's tile-repository contract — `currentState()` + `refresh()` + `ThrottleResettable` — stands for all three). This change does adjust `HourlyEnergyRepository`'s throttle *cadence* and `DailyEnergyRepository`'s *source* for today's value (Decision 6) — those are in scope; the storage format and per-day immutability rules are not touched.
- Merging `ModuleHealthWorker`'s distinct daily-8pm-array-local schedule into the same periodic cadence as hourly/daily — its scheduling logic (timezone-aware initial delay) stays as its own `PeriodicWorkRequest`; only its Settings-triggered throttle-reset routes through the new scheduler.
- Reworking `ema-api-stub`'s `MatchingEngine` matching semantics — fixing the root cause in the app makes the stub's strict single-use interactions a non-issue for this flow without touching stub code.
- Astronomical (sunrise/sunset-calculated) daylight windows — a fixed 06:00–22:00 array-local window is simple and covers the existing hourly chart's 06:00 start with margin past sunset for long summer days; true astronomical gating is a possible future refinement, not required here.

## Decisions

### 1. `ApiSyncScheduler` is a thin facade over `WorkManager.enqueueUniqueWork(..., REPLACE, ...)`, not a custom debounce timer

A fixed-delay debounce (e.g. "wait 500ms after the last request before firing") was considered and rejected: the observed failure sequence (tap "Use local stub" → scroll → edit ECU-ID → save → navigate to Home) spans several real seconds of UI interaction — far longer than any reasonable debounce window — so a timer-based debounce would not have coalesced it anyway.

`WorkManager`'s own unique-work-replacement semantics solve this correctly at any timing: `enqueueUniqueWork(name, ExistingWorkPolicy.REPLACE, request)` cancels a same-named request that hasn't started yet (a *fast* burst collapses for free) **and** cancels one that's already executing (a `CoroutineWorker` honors coroutine cancellation, so a slow burst's in-flight fetch is abandoned before it can persist a stale result — a *slow* burst collapses too, unlike a timer debounce). Only the last-enqueued request's fetch ever completes and persists.

Each of the three request kinds (opportunistic, forced, settings-changed) uses its own unique work name per data-source-group, so an opportunistic Home-visibility request and a forced pull-to-refresh don't cancel each other out of turn, but repeated requests of the *same* kind do coalesce.

**Alternative considered**: a `Mutex`/`Job`-cancellation pattern inside a long-lived singleton (no WorkManager). Rejected — this reintroduces the exact problem the current code has: a coroutine scoped to *something* that can die (a Fragment's `lifecycleScope`, or a process that gets killed) loses in-flight work. WorkManager's request survives process death and re-runs on next opportunity, which is the behavior already relied on for the existing periodic workers.

### 2. Fetch execution moves into a `CoroutineWorker`; Fragments only render `currentState()` and observe completion

`HomeFragment` no longer awaits its own `refresh()` call. `onResume()`/`onPullToRefresh()` call `ApiSyncScheduler.requestOpportunisticSync(context)` / `requestForcedSync(context)` (fire-and-forget — returns immediately, doesn't block or own the fetch) and separately collect `ApiSyncScheduler.observeCompletion(context)` — a `Flow` backed by `WorkManager.getWorkInfosForUniqueWorkFlow(name)` — to re-render from `currentState()` once a sync finishes while the fragment is still visible. If the fragment is destroyed mid-sync, the collector cancels (normal `viewLifecycleOwner.lifecycleScope` behavior) but the underlying `WorkManager` request keeps running and persists its result regardless — the next time Home (or a widget) reads `currentState()`, it sees the completed result.

**Alternative considered**: keep fetch execution in the Fragment's coroutine scope and only move *Settings'* force-refresh into a Worker (a more surgical fix, touching less code). Rejected — this only closes the specific bug that was found, not the general problem statement ("centralized scheduler independent of any frontend") the user asked for, and leaves Home's own fetch still vulnerable to the same silent-cancellation-on-navigate-away class of issue.

### 3. `ApiSyncWorker` replaces `WidgetRefreshWorker`; `ModuleHealthWorker` keeps its own periodic schedule

`WidgetRefreshWorker`'s existing 2-hour periodic job and its `isHourlyDataNeeded()`/`isDailyDataNeeded()`/`WidgetUpdater.enabledWidgets()` gating become `ApiSyncWorker`'s steady-state behavior — the same worker class now also handles the three on-demand request kinds (its `doWork()` reads which kind of request it was enqueued for, via input `Data`, and behaves accordingly: opportunistic/periodic = `force=false`; forced = `force=true`; settings-changed = `resetThrottle()` then `force=false`, since a reset throttle already reads as "due").

Module health's daily-8pm-array-local alignment is a fundamentally different scheduling shape (a specific wall-clock time in a specific timezone, not a rolling interval) — collapsing it into `ApiSyncWorker`'s cadence would require either running `ApiSyncWorker` every few minutes (wasteful) or teaching it two different scheduling models. Keeping `ModuleHealthWorker` as its own `PeriodicWorkRequest` is simpler. `ApiSyncScheduler.requestResyncAfterSettingsChange()` still resets module health's throttle (as today) so the *next* 8pm check runs against fresh credentials, and can trigger `WorkManager.enqueueUniqueWork` with a one-time expedited module-health check when the user is testing the local stub, mirroring hourly/daily's immediate-resync UX.

**Module health is never gated.** Unlike hourly/daily, `ModuleHealthWorker.schedule()` is called unconditionally (from `Application.onCreate()`/`MainActivity`, as today) and `doWork()` never consults `isModuleHealthDataNeeded()`, widget placement, or app-foreground state — it runs every day regardless. This is a deliberate, explicit invariant (see the `api-fetch-scheduler` spec's "Alerting data source is never gated" requirement), not an oversight: a user who hides the Module Health *tile* but still wants email/push alerts must keep getting them.

### 4. Widget freshness after a Settings change is a side effect of the same coalesced request, not a separate call

Today, `widgetUpdateAction(context)` is called manually after every `invalidateApiThrottle()` fetch. In the new design, `ApiSyncWorker`'s `doWork()` already calls `WidgetUpdater.enabledWidgets()`-filtered `updateAllAction()` after a successful fetch (mirroring its current post-`configurable-tiles-widgets` behavior) — `requestResyncAfterSettingsChange()` doesn't need its own separate widget-refresh step; it's already covered by the coalesced worker run.

### 5. The background periodic poll is gated on *actual widget placement*, not just Settings-enabled, and runs only during the array's daylight window

`isHourlyDataNeeded()`/`isDailyDataNeeded()` (from `configurable-tiles-widgets`) answer "does any *enabled* tile or widget consume this?" — but a widget can be enabled in Settings and never actually dragged onto a home screen. For the *unattended background* poll specifically (not Home's on-demand triggers, which are user-initiated and always worth attempting), `ApiSyncWorker`'s periodic run additionally checks `GlanceAppWidgetManager(context).getGlanceIds(WidgetClass::class.java).isNotEmpty()` for each widget type that consumes the data source in question, before deciding the source is "needed" for background-polling purposes. If neither placement nor Home being in the foreground applies, the periodic run for that data source is skipped entirely — a user who enables widgets in Settings but never places any, and never opens the app, costs nothing in the background.

Placement changes are detected via each widget's existing `GlanceAppWidgetReceiver` — `onEnabled()`/`onDisabled()` already fire when the first instance is placed / the last instance is removed; these become the hook that (re-)starts or stops `ApiSyncWorker`'s periodic schedule (`WorkManager.enqueueUniquePeriodicWork(..., KEEP, ...)` on `onEnabled()`, `WorkManager.cancelUniqueWork(...)` on `onDisabled()` once no widget of *any* type remains placed).

This placement/foreground/daylight-window gating applies to **hourly's** periodic poll. Daily no longer has a periodic poll of its own — see Decision 6.

### 6. Today's daily total is derived from the hourly snapshot, not a separate API call

`DailyEnergyRepository`'s steady-state fetch (no missing past days — the common case, active essentially all day every day) exists solely to re-fetch *today's* running total. But today's total is exactly `sum(hourly.hours.values())` — data already obtained by `HourlyEnergyRepository`'s own fetch. Once hourly is polling at its own cadence (Decision 5's placement/foreground/daylight gating), a same-purpose independent `getDailyEnergy` call for today is pure duplication.

`DailyEnergyRepository` gains a `todayTotalProvider: () -> Double?` constructor lambda, matching its existing lambda-injection style (`appSecretProvider: () -> String`). `create(context)` wires it to read `HourlyEnergyRepository`'s persisted `currentState().snapshot?.hours?.values?.sum()`. When `refresh()` finds no missing past days, it derives today's cached value from this provider instead of calling `client.getDailyEnergy` — zero API cost, and freshness is exactly as good as hourly's own cadence (which is at least as fresh as daily's old cadence, usually fresher).

Real `getDailyEnergy` calls remain for exactly two cases, both unchanged from today's code path: the one-time full-window historical backfill on first use, and — because a calendar day rolling over makes yesterday a "missing past day" under the *existing* `hasMissingPastDays` check — one authoritative single-date call to lock in each day's final total once it's no longer "today". This deliberately does **not** reuse a possibly-incomplete last-cached hourly snapshot for the just-completed day (e.g. if the app wasn't opened near midnight, the last hourly fetch could predate the day's final production hours); a real API call for that one now-past date keeps "past days are immutable and authoritative" intact. This backfill call needs no daylight-window or widget-placement gating of its own (a past day's total doesn't change with time of day) — just `isDailyDataNeeded()`, checked once at the first trigger after local midnight.

**Consequence — hourly's trigger condition widens**: since Daily's live "today" value now depends on hourly data, the scheduler's periodic-poll "is hourly needed" check becomes `isHourlyDataNeeded() || isDailyDataNeeded()` — hourly must keep polling even if only a Daily consumer (no Hourly-specific consumer) is enabled, or Daily's derived total goes stale with nothing refreshing it.

**Alternative considered**: keep `DailyEnergyRepository`'s independent "today" call but loosen its throttle. Rejected — any independent call duplicates data already being fetched; loosening the throttle only shrinks the waste, it doesn't eliminate it, and buys no freshness `DailyEnergyRepository` doesn't already get for free by reading hourly's cache.

**Proposed schedule** (worst case: every widget enabled *and* placed, app foreground continuously — this is the ceiling this design must stay under, not the typical case, which will cost substantially less):

| Data source | Endpoint | Repo throttle | Active while | Poll interval | Triggers/day | Est. calls/month (×31d) |
|---|---|---|---|---|---|---|
| Module Health | `getBatchInverterEnergy` | 24h | Always (never gated) | Fixed, once @ 8pm array-local | 1 | ~31 |
| Hourly energy | `getHourlyEnergy` | 45min | `isHourlyDataNeeded() \|\| isDailyDataNeeded()` AND (placed+enabled widget or app foreground) | Every 45min, 06:00–22:00 array-local only | ~21 | ~651 |
| Daily energy (backfill only; today's value derived from hourly, see Decision 6) | `getDailyEnergy` | n/a — one-shot per day | `isDailyDataNeeded()` | Once, first trigger after local midnight | 1 | ~31 |
| **Total** | | | | | | **~713** |
| **Headroom** | | | | | | **~287** |

Calls/month is computed as triggers/day × 31 (the longest possible month), not a 30-day average, so the worst-case ceiling is never understated regardless of which month it is.

Hourly's cadence was tightened from an initial 1h proposal to 45min (`HourlyEnergyRepository.THROTTLE_MS` drops from 3,600,000ms to 2,700,000ms) for better freshness on the visually prominent chart, while a full 30-min cadence was evaluated and rejected: 32 triggers/day × 31 = ~992/month for hourly alone, which combined with Module Health (~31) already exceeds the 1,000 ceiling before Daily is even counted, leaving no margin for a bad-network retry month or a future tile. 45min leaves a healthy ~287/month headroom while still roughly halving worst-case staleness versus the original 1h proposal.

This table is also a **large freshness and budget improvement** over the app's original flat every-2h-including-overnight schedule (~372/month for hourly alone at that cadence, frequently stale by 2–3h even at midday) — overnight polling and daily's redundant per-trigger fetch were both pure waste, since nothing produces at 2am and daily's data was always one hourly-sum away for free.

One conservative assumption: this table counts every trigger as a billed call. ADR-009 confirms only EMA responses with `code == 0` are billed; the app treats `code == 1001` ("no data", e.g. the 06:00 trigger before the array has produced anything yet, or a 21:00 trigger after sunset) as an internal `Success` for caching purposes, but it's unconfirmed whether the real EMA API bills a `1001` response the same as a `0` — this table may be a slight overestimate.

**Alternative considered**: astronomical (sunrise/sunset) daylight bounds instead of a fixed 06:00–22:00 window. Rejected for now (see Non-Goals) — a fixed window is simple and avoids introducing sunrise/sunset calculation as a new dependency; a future change could compute both from a shared constant if seasonal accuracy becomes worth the complexity.

## Risks / Trade-offs

- **[Risk]** `WorkManager`'s `REPLACE` cancellation is best-effort — a `CoroutineWorker` only observes cancellation at suspension points (e.g. between HTTP calls, not mid-socket-read). A fetch cancelled *just* after its HTTP call returns but *before* it persists could theoretically still race a replacement. → **Mitigation**: persistence happens immediately after a successful response parse, before any further suspension; the window is narrow and — critically — no narrower than today's `viewLifecycleOwner.lifecycleScope.launch{}` cancellation, which has the identical property. This is not a regression.
- **[Risk]** Moving fetch execution off the Fragment's lifecycle scope means a sync can complete *after* the user has left Home, silently updating persisted state with no visible confirmation. → **Mitigation**: this is the same behavior periodic background workers already have today (`WidgetRefreshWorker`, `ModuleHealthWorker`) — extending it to on-demand requests is consistent, not novel, and Home already renders from persisted `currentState()` on next visit regardless of what triggered the update.
- **[Risk]** Existing tests (`SettingsWidgetRefreshTest`, `HomeWidgetUpdateTest`, `WidgetRefreshWorkerTest`) assert synchronous call counts immediately after triggering an action (`idle()` then assert) — routing through `WorkManager` changes the execution model enough that these tests need rework, not just renaming. → **Mitigation**: `androidx.work:work-testing`'s `WorkManagerTestInitHelper` + `TestDriver` (already a documented pattern per `ai/lessons-learned.md`'s WorkManager entry) makes worker execution synchronous/controllable in Robolectric; tasks below budget for a full rewrite of these suites, not a patch.
- **[Risk]** `GlanceAppWidgetReceiver.onEnabled()`/`onDisabled()` are the documented hooks for "first instance placed"/"last instance removed", but if a placement change is ever missed (e.g. a rare system-level widget-restore-on-reinstall path that bypasses the normal callback), the periodic schedule could stay stopped when a widget is actually present, going stale until the app is next opened (which re-syncs opportunistically and can re-arm the schedule as a safety net). → **Mitigation**: also re-check placement (and re-arm if needed) from `ApiSyncScheduler.requestOpportunisticSync()` (i.e. every Home visit), not only from the widget lifecycle callbacks — two independent triggers for the same invariant, not a single point of failure.
- **[Risk]** The proposed schedule's ~713/month (31-day basis) is a *ceiling* computed for the worst case (every widget placed, app foreground constantly) and leaves less headroom (~287) than ADR-009's original ~430 — the allocation table in ADR-009 must be updated to reflect this new shape (replacing the flat "every 2h" rows), and this ceiling should be re-validated if a future change adds a new EMA-API-backed tile/widget, per ADR-009's existing design-constraints process. → **Mitigation**: task list includes updating ADR-009's table as part of this change, not as a follow-up.
- **[Risk]** `DailyEnergyRepository` deriving today's total from `HourlyEnergyRepository`'s cache (Decision 6) creates a real dependency between two previously-independent tile repositories — if Daily is enabled but Hourly's own consumers are all disabled, Daily's freshness now silently rides on the widened `isHourlyDataNeeded() || isDailyDataNeeded()` gate rather than its own throttle. A bug in that widened check would make Daily's displayed "today" value go stale with no error state (hourly fetches would simply stop, and `DailyEnergyRepository` has no way to distinguish "hourly is stale because nothing needs it" from "hourly is stale because of a fetch failure"). → **Mitigation**: task list includes an explicit regression test asserting hourly keeps polling when only `isDailyDataNeeded()` is true; `DailyEnergyRepository`'s existing `FetchError` field continues to reflect its own backfill-call failures, which is a distinct (and correctly separate) concern from live-today staleness.

## Migration Plan

No data migration — this is a pure control-flow refactor; no SharedPreferences schema changes. Rollout is a single change (not incremental/flagged): once merged, all three frontends route through the new scheduler simultaneously, since a half-migrated state (e.g. Home using the new path while Settings still calls `refresh()` directly) would reintroduce exactly the coordination gap this change closes.

## Open Questions

- **How does the periodic background job know "app is foreground" without a widget placed?** The proposed schedule's "or app foreground" condition (Decision 5) needs a concrete signal — likely `androidx.lifecycle.ProcessLifecycleOwner` observed from `Application.onCreate()`, persisting a simple "app foregrounded at time T" flag `ApiSyncWorker` can check, rather than anything Fragment-scoped (which wouldn't survive process death for the Worker to read). This needs to be nailed down in Section 1/5's implementation tasks; the schedule/budget math doesn't change based on the answer, only whether "app open with zero widgets placed" gets background-poll freshness or relies solely on `onResume()`-triggered on-demand fetches (which would still be correct, just less proactive between visits).
