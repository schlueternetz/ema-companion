## Context

`ema-api-stub` (`code/ema-api-stub/`) is a standalone Ktor project, already specified and archived (`openspec/specs/ema-api-stub/`), that serves scripted EMA API responses via ordered per-ECU-id "interactions" with a strict-sequential cursor. Nothing in the Android app's automated tests currently launches it: `HomeProductionIntegrationTest` hand-copies the bundled Good Data scenario's JSON body into a `MockWebServer`, and the `hourly`/`daily` endpoints added by `production-data-and-graphs` have no stub coverage at all.

Separately, while scoping this change, running the stub's own test suite (`cd code/ema-api-stub && ./gradlew test`) showed 7 failing tests: `ScenarioLoader.loadDefault()` throws `ScenarioLoadException: Duplicate scenario for ECU id 203000001234`, because `module-health-*-203000001234.json` (added in `module-health-tile`) reuses the same `ecuId` as the bundled `203000001234.json`, which the loader's own documented "fail fast on duplicate" behavior correctly rejects. This change fixes that collision (decision 8) since both the debug "Use local stub" shortcut and the stub-backed Maestro flow depend on `loadDefault()` actually succeeding. This change's *new tests*, however, still must not depend on `loadDefault()` succeeding, in case the fix regresses — see decision 2.

## Goals / Non-Goals

**Goals:**
- Add `hourly`/`daily` scenario interactions to the stub so those endpoints have real coverage
- Replace the hand-copied JSON pattern in `HomeProductionIntegrationTest` with one that reads the actual scenario file, so the fixture cannot silently drift
- Add embedded (in-process, no real socket) integration tests driving `OkHttpEmaApiClient` + `HourlyEnergyRepository`/`DailyEnergyRepository` through the stub's matching engine
- Add a debug-build-only "Use local stub" Settings action so local development defaults to free stub calls instead of real, budget-counted EMA API calls
- Fix `ema-api-stub`'s pre-existing `loadDefault()` duplicate-ECU-id collision so the stub's own `./gradlew test` is green and the bundled default set (used by the debug shortcut and by Maestro, see below) actually loads
- Drive the critical Home Maestro flow against a live local stub instance so the golden path is verified against real, populated data — not just the placeholder/error path that dummy unreachable credentials exercise today
- Bring `docs/ema-api-stub/README.md` and `docs/getting-started.md` up to date with the above

**Non-Goals:**
- Testing HMAC/request-signing correctness via the stub — it doesn't verify `X-CA-*` headers by design (documented caveat); signing stays covered by the existing `EmaRequestSigner` reference-HMAC unit test
- Changing the persisted Base URL default or the "Reset to default" action for any build type — both remain unconditionally the production URL, in every build type, always
- Adding stub support for endpoints `OkHttpEmaApiClient` doesn't call, or for `/installer/api/v2/`
- Broadening Maestro coverage beyond the existing Home flow (e.g. a dedicated stub-only flow) — extending the one flow that already covers Home is enough per ADR-002's "small set of critical flows" scope

## Decisions

1. **Embedded engine over a live server process for tests.** Integration tests use Ktor's `testApplication` / a directly-constructed `MatchingEngine`, matching the stub's own test pattern — no real socket, no port to manage, deterministic. A live `./gradlew run` process remains a manual-dev-only tool (used by the new debug Settings action, not by automated tests).

2. **Load fixtures via `ScenarioLoader.loadFromDirectory` against a scoped directory, not `loadDefault()`.** Each new test writes just the JSON file(s) it needs into a JUnit `TemporaryFolder` (mirroring `ScenarioLoaderTest`'s existing pattern) rather than loading the full bundled `scenarios/` set. This decouples these tests from the pre-existing duplicate-ECU-id collision entirely — they pass regardless of that bug's state — and keeps each test's fixture minimal and legible.

3. **Append `hourly` and `daily` interactions to the existing `203000001234.json`, directly after `minutely`.** This keeps "Good Data" as one canonical persona (10 kW array at 80%) rather than fragmenting it across ECU ids. Because matching is strict-sequential per ECU, a test that loads this specific file and wants only `hourly` (not `minutely` first) instead uses its own minimal single-interaction fixture (decision 2) — nothing is forced through an unrelated endpoint first. Also add a `code:1001` no-data interaction and a two-calendar-month `daily` case, each as their own small dedicated fixture rather than folding into the shared file.

4. **`HomeProductionIntegrationTest` reads the real `203000001234.json` resource instead of a hand-typed string.** This is the one test where fidelity to the actual bundled file is the point (it exists to prove the fixture doesn't drift), so it loads the file's first interaction's response body directly rather than duplicating it inline.

5. **Debug-only "Use local stub" is a stateless action, not a new persisted mode.** Gated by `BuildConfig.DEBUG`, it calls the existing `SettingsRepository.setBaseUrl(...)` / save path with a computed default (`http://10.0.2.2:${BuildConfig.STUB_PORT}/user/api/v2/` — the standard Android-emulator-to-host-loopback address; port sourced per decision 7). No new stored flag, no new reset/migration logic — it's the same save a developer could do by hand, just one tap. Release builds never see the action (view removed/gone, verified by a config-gated test), so the persisted default and "Reset to default" stay untouched by this change.

6. **Documentation is additive**, not a new doc file: extend `docs/ema-api-stub/README.md`'s existing "Using the stub from the Companion app / integration tests" section (also fix its stale endpoint table while touching it — it currently omits module-health, and would otherwise now also omit hourly/daily) and add a short section to `docs/getting-started.md` framing stub=dev/test vs real API=prod.

7. **Debug shortcut's port comes from a `STUB_PORT` build property, not a hardcoded `8080`.** `app/build.gradle.kts` adds `buildConfigField("String", "STUB_PORT", "\"${project.findProperty("STUB_PORT") ?: System.getenv("STUB_PORT") ?: "8080"}\"")`, reusing the exact property/env-var name the stub server itself already reads (`Application.kt`'s `STUB_PORT` env var), so a developer who runs the stub on a non-default port sets the same name in one place (`local.properties` or `-PSTUB_PORT=`) and both sides agree. The shortcut builds its URL as `http://10.0.2.2:${BuildConfig.STUB_PORT}/user/api/v2/`. Defaults to `8080` when unset, matching the stub's own `DEFAULT_PORT`.

8. **Fix the `loadDefault()` duplicate-ECU-id collision by reassigning distinct ECU ids to the three module-health scenario files**, rather than changing loader behavior (the "fail fast on duplicate" contract is correct and stays). New ids: `module-health-all-healthy-203000001234.json` → `203000005678`, `module-health-one-offline-1day-203000001234.json` → `203000009012`, `module-health-one-offline-3day-203000001234.json` → `203000003456` (filenames keep their existing `-203000001234` suffix as-is — only the internal `ecuId` field and the ECU id used inside each file's own interactions change — filename churn is out of scope and the filename is documented as non-authoritative). Confirmed safe: `ModuleHealthIntegrationTest` mocks HTTP responses directly via `MockWebServer` and never loads these stub files, so nothing on the Android side references these ids.

9. **Extend the existing `a-home-screen.yaml` Maestro flow, not a new flow file.** After its current dummy-credential/placeholder-path assertions, the flow additionally: taps the new debug-only "Use local stub" action, edits the ECU-ID field to the stub's canonical Good Data id (`203000001234` — matches the bundled scenario, and the stub wildcards `sid`/App-ID/App-Secret since it never verifies HMAC), then re-opens Home and asserts the real values render (`Current Production: 8000 W`, populated hourly/history charts). One flow keeps this within ADR-002's "small set of critical flows" and avoids reintroducing the accessibility-driver-degradation ordering problem a 4th flow would risk (see `ai/lessons-learned.md`, 2026-07-03) — `a-home-screen.yaml` already runs first for that exact reason. Both the placeholder-path and real-data-path assertions now live in one flow, back to back.

10. **CI launches the stub as a background process for the `e2e` job only.** `.github/workflows/ci.yml`'s `e2e` job starts `./gradlew run` from `code/ema-api-stub` in the background before `maestro test maestro/`, polls (`curl` retry loop) until the port responds, then proceeds; no explicit teardown step is needed since the job's runner/VM is destroyed after the job regardless. Locally, `docs/getting-started.md` documents starting the stub manually (`cd code/ema-api-stub && ./gradlew run`) before running `/qa`'s Maestro step.

## Risks / Trade-offs

- [Risk] Appending `hourly`/`daily` after `minutely` in `203000001234.json` could tempt a future test to load the whole file and expect all three in one call sequence → Mitigation: only `HomeProductionIntegrationTest` (which calls `minutely` alone) uses the shared file as-is; document in the scenario file's own `description` field that hourly/daily tests should use isolated fixtures.
- [Risk] Hardcoded `10.0.2.2` only resolves to the host from an Android emulator, not a physical device → Mitigation: acceptable as a convenience default; a developer on physical hardware edits the field manually, same as today.
- [Risk] `BuildConfig.DEBUG` gating regresses and the action ships in release → Mitigation: single visibility call site plus a Robolectric test asserting the view is gone under a release-configured build.
- [Risk] Running a second background process (the stub) alongside the emulator in CI adds a new source of `e2e` job flakiness (port not ready in time, process fails silently) on top of the already-flaky Maestro/emulator combination documented in `ai/lessons-learned.md` → Mitigation: readiness poll with a bounded retry/timeout before Maestro starts, so a slow-starting stub fails loudly (job error) instead of Maestro racing an unready server and producing a confusing flow failure.
- [Risk] Extending `a-home-screen.yaml` with more steps (stub shortcut, ECU-ID edit, re-navigation, more assertions) makes an already-long, driver-order-sensitive flow longer → Mitigation: it's still one flow (no new ordering interactions to reason about), and the new steps come after the existing ones, so a regression there doesn't retroactively explain away the already-passing placeholder-path assertions.
